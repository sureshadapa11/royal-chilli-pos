# Royal Chilli POS — API Reference

Reference documentation for every route handler under `app/api/**/route.ts` (85 route files, 129 method handlers). Generated by reading each route file's source directly — no guessing on auth/body shapes; anything ambiguous is called out explicitly instead of asserted.

## Conventions

- **Session cookie**: `POST /api/auth/login` verifies `{ name, pin }` against `staff.pin_hash` (bcrypt), then signs a JWT (`jose`, `HS256`, 12h expiry, secret from `JWT_SECRET` env var, fallback dev secret hardcoded in `lib/auth.ts`) containing `{ id, name, role }`. The JWT is set as an **httpOnly, `sameSite=lax`, 12h-maxAge cookie named `pos_session`** (`secure` flag on in production). `POST /api/auth/logout` deletes the cookie. Every other route reads it back via `getSessionFromRequest(req)` (route handlers) or `getSession()` (server components), both in `lib/auth.ts`, which verify the JWT and return `{ id, name, role } | null`.
- **Permission system**: `lib/permissions.ts` exposes six gate functions — `canManageStaff`, `canManageInventory`, `canViewCrm`, `canManageCrm`, `canManageDrivers`, `canManageFinance` — each taking the session's `role` and returning a boolean. Most write (and many read) endpoints call `getSessionFromRequest` then one of these. The role→permission mapping is **configurable at runtime**: it lives in the `role_permissions` table, is cached in-process, refreshed on every edit, and edited via `GET`/`PUT /api/permissions` (surfaced in the Settings UI). If the table can't be reached the code falls back to a hardcoded default mapping baked into `lib/permissions.ts` (fail-closed, not fail-open). A handful of routes instead do a direct role check (e.g. `session.role === "owner" || session.role === "admin"` on `/api/permissions` PUT, or `session.role === "driver"` on `/api/drivers/status`).
- **Error shape**: consistently `{ error: string }` with the HTTP status carrying the meaning — `400` for validation failures, `401` for missing/invalid session or failed permission check, `403` for an authenticated-but-wrong-owner action (e.g. a driver touching someone else's delivery), `404` for missing resources, `409` for a rota scheduling conflict, `500` for unexpected/DB errors. Success responses are `NextResponse.json({ success: true, ... })` (mutations) or a bare data object (GETs), status `200` unless noted (`201` on most creates).
- **Unauthenticated routes**: only `app/api/public/**` (customer-facing ordering/reservation/QR-table-ordering flows, called from the public website with no staff session) and `POST /api/auth/login` (how a session is obtained) are unauthenticated by design. `GET /api/staff` is also intentionally unauthenticated (login-screen name picker; exposes only `id/name/role`). A few other routes were found with **no session check in the code** despite not being under `/api/public` — these are flagged individually below and in the summary at the end; they are not necessarily intentional.

## 1. Authentication (`/api/auth/*`)

### `POST /api/auth/login`
**Auth:** none (this is how a session is obtained)
**Body:** `{ username: string, password: string, pair_till?: boolean }`
**Response:** `{ success: true, user: { id, name, role, businessId } }`, sets `pos_session` cookie (and the till cookie when a manager sends `pair_till: true`)
Looks up active `staff` by `username`, compares `password` against `password_hash` with bcrypt. `401` with the same message for an unknown username or a wrong password. The session's business is the staff member's **own** business (`staff.business_id`) whatever domain they sign in on; only the group owner starts in the business whose domain they're on (`loginBusinessId`, else The Royal Chilli). `403` if the account isn't set up at any business. Every successful sign-in writes an `audit_logs` row (`action: "staff_login"`, `changes: { host, domain_business_id, business_id }`) so a sign-in from another business's domain — or an unknown one (`domain_business_id: null`) — can be diagnosed.

#### Which business a domain belongs to
- `businessForHost(host)` matches `businesses.domain` (case-insensitive, `www.` and port ignored) and returns `null` for an unknown domain (a mistyped URL, the `*.vercel.app` address, `localhost`).
- `businessForHostOrNull(host, pick?)` does the same but first honours `?b=<slug>` for an **active** business, and never falls back to The Royal Chilli.
- The staff login screen (`/login`) uses `businessForHostOrNull`: a known domain (or `?b=<slug>`) shows that business's name, logo (initials if none) and brand colour; an **unknown domain shows "Business not found — check the web address"** with no business's branding. The form still works there — staff land in their own business.
- **`?b=<slug>` workaround** for a business in transition (no domain of its own yet, e.g. Melt House while its old site is still live): links and table QR codes can add `?b=melt-house` to any address — `/login?b=melt-house` (staff sign-in) and `/table/5?b=melt-house` (QR table ordering, `/api/public/tables/*`). Once `businesses.domain` is set, the domain works on its own and the existing `?b=` links keep working.
- The public website / customer APIs (`websiteBusinessId`) still treat an unknown domain as The Royal Chilli for now, so the current site keeps working until every business's domain is set.

### `POST /api/auth/logout`
**Auth:** none required
**Body:** none
**Response:** `{ success: true }`, deletes `pos_session` cookie

### `GET /api/auth/me`
**Auth:** session required (any role)
**Response:** `{ user: { id, name, role } }` or `401 { error: "Unauthorized" }`

## 2. Public Website (`/api/public/*`)

All routes in this section are **unauthenticated by design** — they back the customer-facing ordering / reservation / QR-table-ordering flows on the public website, so no session cookie is expected or checked.

### `GET /api/public/delivery-zones/check`
**Auth:** none
**Query:** `postcode` (required)
**Response:** `{ deliverable: false }` or `{ deliverable: true, fee, min_order, zone_name }`
Delegates to `matchDeliveryZone()` in `lib/delivery-zones.ts`.

### `POST /api/public/orders`
**Auth:** none
**Body:** `{ order_type: "takeaway"|"delivery", customer_name, customer_phone, customer_address?, customer_postcode?, notes?, scheduled_for?, items: [{ menu_item_id, quantity, notes?, selected_options? }] }`
**Response:** `201 { success: true, order_number, total, scheduled_for }`
Validates order_type enum, required contact fields, delivery address/postcode when `order_type=delivery`, non-empty cart, and (if present) `scheduled_for` via `validateScheduledTime`. Server resolves each item's price/name and modifiers server-side via `resolveItemWithModifiers` — **client-submitted prices are never trusted**. Delivery orders are matched against a zone and rejected if unreachable or below `min_order`. Auto-creates/matches the customer by phone (`findOrCreateCustomerByPhone`), attaches to the currently open work period if any, and inserts `orders`/`order_items`/`order_item_modifiers`.

### `POST /api/public/reservations`
**Auth:** none
**Body:** `{ customer_name, customer_phone, party_size?, reservation_date, reservation_time, notes?, join_waitlist? }`
**Response:** `{ full: true, message }` (slot full, offers waitlist) or `201 { success: true, id, waitlisted: boolean }`
Capacity check compares reservation count for that date/time against the actual number of `restaurant_tables` rows — not a hardcoded guess. Auto-creates/matches customer by phone.

### `POST /api/public/tables/:tableNumber/order`
**Auth:** none
**Body:** `{ items: [...] }`
**Response:** `{ success: true, order: {id, order_number, status, total}|null, items }`
QR-code "add items to my table's open order" flow; delegates to `lib/dine-in.ts` (`getTableByNumber`, `addItemsToTable`).

### `POST /api/public/tables/:tableNumber/request`
**Auth:** none
**Body:** `{ type: "waiter"|"bill" }`
**Response:** `{ success: true }`
Inserts a row into `table_requests` (status `pending`) — surfaced to staff via `GET /api/table-requests`.

### `GET /api/public/tables/:tableNumber`
**Auth:** none
**Response:** `{ table, order: {id, order_number, status, total}|null, items }`
QR-code table landing page — current table state and open order/items, if any.

## 3. Orders / POS (`/api/orders/*`, `/api/kitchen`, `/api/tables`, `/api/table-requests`, `/api/work-periods`)

### `GET /api/orders`
**Auth:** session required (any role)
**Query:** `status` (`"open"` = any non-paid/cancelled order, or an exact status), `date` (YYYY-MM-DD), `table_id`, `order_type`, `source` (`"website"` filters to customer self-service orders with no `staff_id`)
**Response:** `{ orders: [...] }` — table number and staff name flattened in from FK joins

### `POST /api/orders`
**Auth:** session required (any role)
**Body:** `{ order_type, table_id?, customer_name?, customer_phone?, customer_address?, items: [{menu_item_id?, item_name, item_price, quantity, notes?}], notes?, discount?, discount_reason? }`
**Response:** `201 { success: true, order, items }`
Staff-side POS order creation. Computes subtotal/tax (flat 20% VAT)/total server-side from submitted `item_price` — note this endpoint (unlike the public one) does **not** re-resolve prices from the menu table, it trusts the POS client's line items. Attaches to open work period; marks table `occupied` if dine-in.

### `GET /api/orders/:id`
**Auth:** session required (any role)
**Response:** `{ order, items }` or `404`

### `PUT /api/orders/:id`
**Auth:** session required (any role)
**Body:** `{ status?, discount_type?: "percent" | "amount" | null, discount_value?, discount_reason?, notes? }`
**Response:** `{ success: true, order }` or `409` if `discount_type` is sent for an order that's already fully paid.
Updating `status` to `paid`/`cancelled` frees the table. Setting `discount_type`/`discount_value` recomputes `tax`/`discount`/`total` via `lib/order-totals.ts`'s `recalcTotals` (subtotal → VAT → discount → service charge → total) — `discount_value` is a percentage (0-100) when `discount_type` is `"percent"`, or a flat pound amount when `"amount"`. Pass `discount_type: null` to clear it.

### `DELETE /api/orders/:id`
**Auth:** session required (any role)
**Response:** `{ success: true }`
Soft-delete: sets `status="cancelled"` (does not actually delete the row) and frees the table.

### `POST /api/orders/:id/assign-driver`
**Auth:** `canManageDrivers(session.role)`
**Body:** `{ driver_id: number }`
**Response:** `{ success: true, order }`
Validates the target staff member has `role="driver"`. Sets `delivery_status="assigned"`.

### `POST /api/orders/:id/delivery-status`
**Auth:** session required, plus the order's `driver_id` must equal `session.id` (`403` otherwise — a driver can only update their own delivery)
**Body:** `{ status: "out_for_delivery"|"delivered" }`
**Response:** `{ success: true, order }`
Enforces a fixed state machine (`assigned→out_for_delivery→delivered`); any other transition is `400`. Marking `delivered` also sets order `status="paid"` (cash-on-delivery orders are considered settled on delivery).

### `GET /api/orders/:id/items`
**Auth:** **no session check present in the code** (flagged — see summary)
**Response:** `{ items }` with `is_veg` flattened in from the joined `menu_items` row

### `POST /api/orders/:id/items`
**Auth:** session required (any role)
**Body:** `{ items: [{menu_item_id?, item_name, item_price, quantity, notes?}] }`
**Response:** `{ success: true, insertedIds }`
Adds items to an existing order and calls `recalcTotals(id, businessId)` afterward (`lib/order-totals.ts`).

### `PUT /api/orders/:id/items`
**Auth:** session required (any role)
**Body:** `{ itemId, action?: "void"|"reduce", quantity?, status? }`
**Response:** `{ success: true }`
`action="void"` cancels one line item and recalcs totals; `action="reduce"` (with `quantity>0`) lowers the line's quantity and recalcs; otherwise a bare `status` update on the item (e.g. kitchen prep status) with no totals recalc.

### `POST /api/orders/:id/payment`
**Auth:** session required (any role)
**Body:** `{ method, amount, tip_amount?, change_given?, reference?, extraOrderIds?: number[] }`
**Response:** `{ success: true, fully_paid: boolean, remaining_balance: number }`
Rejects payment if the order is already `paid`, and rejects `amount` that exceeds the remaining balance (with a small epsilon for rounding). Inserts a `payments` row — a DB trigger updates `orders.amount_paid`. Order flips to `status="paid"` only once `amount_paid >= total`; only then is the table freed and loyalty points awarded (`awardPurchasePoints`). Partial payments are fully supported. `extraOrderIds` lets a single payment settle multiple merged orders at once — each gets its own real `payments` row (not just a status flip) so cash/card reporting totals stay accurate.

### `POST /api/orders/:id/service-charge`
**Auth:** session required (any role)
**Body:** `{ pct: number }` (0–100)
**Response:** `{ success: true, order }` or `409` if the order is already fully paid.
Sets `service_charge_pct` then calls `recalcTotals(id, businessId)`.

### `GET /api/kitchen`
**Auth:** **no session check present in the code** (flagged — see summary)
**Response:** `{ orders }` — orders with status `sent_to_kitchen` or `ready`, each with its `items` attached, oldest first

### `PUT /api/kitchen`
**Auth:** **no session check present in the code** (flagged — see summary)
**Body:** `{ orderId, status }`
**Response:** `{ success: true }`
Kitchen display's status-advance action (e.g. mark ready).

### `GET /api/tables`
**Auth:** **no session check present in the code** (flagged — see summary)
**Response:** `{ tables }`

### `POST /api/tables`
**Auth:** **no session check present in the code** (flagged — see summary)
**Body:** `{ table_number, capacity?, location? }`
**Response:** `201 { success: true, table }`

### `PUT /api/tables`
**Auth:** **no session check present in the code** (flagged — see summary)
**Body:** `{ id, status?, capacity?, location?, table_number? }`
**Response:** `{ success: true }`

### `GET /api/table-requests`
**Auth:** session required (any role)
**Response:** `{ requests }` — pending `table_requests` (waiter/bill calls), oldest first

### `PATCH /api/table-requests`
**Auth:** session required (any role)
**Body:** `{ id }`
**Response:** `{ success: true }`
Marks a request `resolved`.

### `GET /api/work-periods`
**Auth:** session required (any role)
**Response:** `{ period, summary: { total_revenue, total_orders, cash_total, card_total, open_orders } }`
Returns the currently open work period (if any) plus today's revenue/payment-split summary.

### `PUT /api/work-periods`
**Auth:** session required (any role)
**Body:** `{ closing_cash?, staff_id? }`
**Response:** `{ period }` or `404` if no period is open
Closes the currently open work period.

### `POST /api/work-periods`
**Auth:** session required (any role)
**Body:** `{ opening_cash?, staff_id? }`
**Response:** `{ period }`
Opens a new work period ("start of shift" till float).

**Auth:** session required (any role)
**Query:** `date` (exact match) or `from` (>= date, "upcoming" view — used by `/pos/reservations`, which lists every booking from today onward with no date picker), `status`. `date` wins if both are given.

**Body:** `{ customer_name, reservation_date, reservation_time, customer_phone?, customer_email?, party_size?, table_id?, notes?, source? }`
**Response:** `201 { success: true, reservation }`
Staff-side booking creation — unlike the public endpoint, does no capacity/waitlist check.

### `PUT /api/reservations`
**Auth:** session required (any role)
**Body:** `{ id, status, table_id?, notes? }` — `status` must be one of `pending|confirmed|seated|cancelled|no_show|waitlisted`

`status="seated"` marks the table `occupied`; `cancelled`/`no_show` frees it.

## 6. Delivery Zones & Drivers (`/api/delivery-zones/*`, `/api/drivers/*`)

Drivers are staff with `role="driver"` (migration `091_driver_role.sql`). They sign in like other staff and land on `/staff/drivers` ("My Deliveries"); managers/admins (`canManageDrivers`) get the roster + assignment view on the same page, linked as 🚗 **Drivers** in the Staff Hub menu.

> **Scoping:** driver calls are auto-scoped — `my-deliveries` filters on `driver_id = session.id`, `PATCH /api/drivers/status` only updates the caller's own `staff` row, and `delivery-status` rejects (`403`) any order not assigned to the caller. All order reads/writes go through `bizDb(session.businessId)`, so a driver can never see or change another business's orders, and managers can only assign drivers who belong to their own business. Covered by `app/api/drivers/__tests__/route.test.ts`.

### `GET /api/delivery-zones`
**Auth:** `canManageDrivers(session.role)`
**Response:** `{ zones }`

### `POST /api/delivery-zones`
**Auth:** `canManageDrivers(session.role)`
**Body:** `{ name, postcode_prefixes: string[], fee?, min_order? }` — name + ≥1 prefix required
**Response:** `201 { success: true, zone }`
Postcode prefixes are normalized (trim + uppercase) before storing.

### `PATCH /api/delivery-zones/:id`
**Auth:** `canManageDrivers(session.role)`
**Body:** any subset of `name, postcode_prefixes, fee, min_order, active`
**Response:** `{ success: true, zone }`

### `DELETE /api/delivery-zones/:id`
**Auth:** `canManageDrivers(session.role)`
**Response:** `{ success: true }` (500 with friendly message if referenced by a past order)

### `GET /api/drivers`
**Auth:** `canManageDrivers(session.role)`
**Response:** `{ drivers }` — active `staff` with `role="driver"`, each enriched with `delivered_count`/`delivered_value` computed from their delivered orders

### `GET /api/drivers/my-deliveries`
**Auth:** session required (any role) — implicitly scoped to `session.id` via the `driver_id` filter, so a non-driver would just get an empty list
**Response:** `{ deliveries }` — the caller's own orders with `delivery_status` in `assigned`/`out_for_delivery`

### `PATCH /api/drivers/status`
**Auth:** session required + `session.role === "driver"` (`403` otherwise)
**Body:** `{ status: "available"|"on_delivery"|"offline" }`
**Response:** `{ success: true }`
Updates the caller's own `staff.driver_status`.

### `GET /api/drivers/unassigned-orders`
**Auth:** `canManageDrivers(session.role)`
**Response:** `{ orders }` — non-cancelled delivery orders with `delivery_status="unassigned"`

## 7. Staff & Attendance (`/api/staff`, `/api/employees/*`, `/api/attendance/*`, `/api/availability`, `/api/leave-requests/*`, `/api/rota/*`)

### `GET /api/staff`
**Auth:** none (intentionally — code comment: login-screen name picker needs this before any session exists; only exposes `id, name, role`)
**Response:** `{ staff }` — active staff only

### `POST /api/staff`
**Auth:** `canManageStaff(session.role)`
**Body:** `{ name, pin, role }` — all required
**Response:** `201 { success: true, staff: {id, name, role} }`
Simple staff creation (PIN hashed with bcrypt). Distinct from the richer `/api/employees` create.

### `GET /api/employees`
**Auth:** `canManageStaff(session.role)`
**Query:** `search` (matches name/employee_number/email), `role`, `active` (default `"1"`; pass `"all"` to include inactive)
**Response:** `{ employees }` — full HR profile field set, each with `location_ids: number[]` (assigned locations; `[]` = unassigned, no location access)

### `POST /api/employees`
**Auth:** `canManageStaff(session.role)`
**Body:** `{ name, pin, role, email?, phone?, address?, date_of_birth?, hire_date?, employment_type?, pay_rate?, pay_frequency?, emergency_contact_name?, emergency_contact_phone?, notes?, vehicle_type?, vehicle_registration?, driver_status? }`
**Response:** `201 { success: true, employee }`
Enforces an optional `max_employees` cap read from `app_settings` (only if that setting exists). Auto-generates `employee_number` as `RC-EMP-####` from the new row's id. Writes an `audit_logs` entry.

### `GET /api/employees/:id`
**Auth:** `canManageStaff(session.role)`
**Response:** `{ employee }` (including `location_ids: number[]`) or `404`

### `PATCH /api/employees/:id`
**Auth:** `canManageStaff(session.role)`
**Body:** any subset of the editable HR fields, plus optional `pin` (rehashed if present)
**Response:** `{ success: true, employee }`
Writes an `audit_logs` entry with the diff.

### `PATCH /api/staff/:id/locations`
**Auth:** `canManageStaff(session.role)`; the staff member must belong to the session's business (`404` otherwise)
**Body:** `{ location_ids: number[] }` — replaces the staff member's assignments. `[]` unassigns them: they have **no** location access (location analytics shows them no locations and inventory endpoints reject them) until they're reassigned. They can still sign in — sign-in never checks locations.
**Response:** `200 { success: true, staff: { id, name, location_ids } }`
- `400` if `location_ids` isn't an array of positive integers, or any id isn't a location of this business (cross-business ids are rejected and nothing changes).
- `400` if a manager tries to remove their own last location (keep at least one).
- `403` if the caller tries to add or remove a location they aren't assigned to themselves. Only the group owner isn't limited, so an unassigned manager can't assign anyone until the owner assigns them.
- Writes an `audit_logs` row: `action: "staff_location_assignment"`, `entity_type: "staff"`, `entity_id`, `changes: { from: [...], to: [...] }`.
The Staff Hub page `/staff/:id/assignments` (linked from HR → employee → **Locations**) edits this with one checkbox per active location. `GET /api/staff/:id/locations` lists the staff member's `locationIds`.

### `POST /api/staff/:id/locations`
**Auth:** `canManageStaff(session.role)`; the staff member must belong to the session's business (`404` otherwise)
**Body:** `{ location_id: number }` — adds one assignment.
**Response:** `201 { success: true, staffId, locationId }`
- `400` if `location_id` isn't a positive integer or isn't a location of this business.
- `403` `"You can only assign locations you're assigned to"` unless the caller is the group owner or is assigned to that location themselves.
- `409` if the staff member is already assigned to it.
- Writes the same `staff_location_assignment` audit log as `PATCH`.

### `DELETE /api/staff/:id/locations/:locationId`
**Auth:** `canManageStaff(session.role)`; the staff member must belong to the session's business (`404` otherwise)
**Response:** `200 { success: true }`
- `403` `"You can only remove locations you're assigned to"` unless the caller is the group owner or is assigned to that location themselves.
- `400` if a manager tries to remove their own last location.
- `404` if the location isn't this business's or the staff member isn't assigned to it.
- Writes the same `staff_location_assignment` audit log as `PATCH`.

### `GET /api/attendance`
**Auth:** `canManageStaff(session.role)`
**Query:** `from`, `to`, `staff_id`, `pending_only` (`"1"` = only pending corrections)
**Response:** `{ clockEvents }`
Manager-wide view across all staff clock events. FK to `staff` is explicitly named (`clock_events_staff_id_fkey`) since `clock_events` has two FKs to `staff` (`staff_id` and `approved_by`).

### `POST /api/attendance/:id/correction`
**Auth:** session required — restricted to the event's own owner (`event.staff_id === session.id`, else `404`)
**Body:** `{ requested_clock_in?, requested_clock_out?, reason }` — reason required
**Response:** `{ success: true, clockEvent }`
An employee requesting a fix to a past clock event.

```json
{

      "id": 1,
      "name": "Kitchen",
      "sales": { "count": 42, "total": 1250.50, "by_channel": { "pos": 800, "online": 450.50 } },

```

- `orders_today`: non-cancelled orders (paid or not) at the location today.
- `top_items`: top 5 items by quantity sold in the range (cancelled lines excluded); `revenue` = quantity × item price.

**Query:** `date` (defaults to today)
**Response:** `{ date, summary, byType, topItems, paymentSplit, hourly }`
Single-day end-of-day report: revenue/order-count summary, breakdown by order type, top 10 items, payment method split, hourly breakdown. Excludes cancelled orders.

### `GET /api/staff-reports`
**Auth:** `canManageStaff(session.role)`
**Query:** `from`, `to` (both required)
**Response:** `{ rows, totals }`
Per-staff rollup of hours worked (`computeHoursForPeriod`), late-clock-in count, and labour cost (from `payroll_entries` whose period falls in range) — plus a `totals` row summing hours/cost across all staff.

## 13. Settings, Permissions & Audit (`/api/settings`, `/api/permissions`, `/api/audit-logs`)

### `GET /api/settings`
**Auth:** `canManageStaff(session.role)`
**Response:** `{ settings }` — flat `{key: value}` map of the `app_settings` table

### `PUT /api/settings`
**Auth:** `canManageStaff(session.role)`
**Body:** arbitrary `{key: value}` map
**Response:** `{ success: true }`
Upserts every key in the submitted object into `app_settings` on conflict `key`.

### `GET /api/permissions`
**Auth:** `canManageStaff(session.role)`
**Response:** `{ matrix, roles, permissions, labels }`
`matrix` is the full role × permission grid, read fresh from `role_permissions` (bypasses the in-memory cache so the editor UI never shows stale state).

### `PUT /api/permissions`
**Auth:** direct role check — `session.role === "owner" || session.role === "admin"` only (**stricter than `canManageStaff`**, and deliberately not itself configurable through the permission system it edits)
**Body:** `{ role: StaffRole, permission: PermissionKey, granted: boolean }`
**Response:** `{ success: true }`
Validates `role`/`permission` against the known enums. Hardcoded guard: **`role === "owner"` is always rejected** (`400 "Owner permissions cannot be changed"`) so an admin can't accidentally strip every owner's access. Upserts into `role_permissions` on `(role, permission)`, then calls `refreshPermissionsCache()` so the change takes effect immediately for every other endpoint.

### `GET /api/audit-logs`
**Auth:** `canManageStaff(session.role)`
**Query:** `limit` (default 100, capped at 500)
**Response:** `{ logs }` — staff name flattened in (falls back to `"System"` for entries with no `staff_id`)

### `GET /api/website/config`
**Auth:** `canAccess(session.role, "website")` (`401` no session, `403` employee/driver)
**Query:** optional `businessId` — another business's id is only allowed for the group owner (`session.owner`, `403` otherwise)
**Response:** `{ business, config, modules, canToggleOrdering, version }` — `version` is `businesses.website_config_version` (migration `094_website_config_version.sql`); `config` is `businesses.website_config` (migration `093_website_config.sql`) filled out to the full shape in `lib/website-config.ts`

### `POST /api/website/config`
**Auth:** `canAccess(session.role, "website")`; always saves to `session.businessId` (a `businessId` in the body for another business → `403`)
**Body:** `{ config?: Partial<WebsiteConfig>, online_ordering?: boolean, version?: number }` — `version` is the one the edit was based on; if someone has saved since → `409 { error, version }` (reload and retry). The update itself is also conditional on the version read, so overlapping saves never overwrite each other. `online_ordering` (the `modules.online_ordering` switch) is owner-only (`403`), same as Settings → Business setup → Modules
**Response:** `{ success: true, business, config, modules, canToggleOrdering, version }` (`400 { error, fields }` on validation failure: length limits, links must be `http(s)`)
Merges into the existing config, bumps `version`, clears the business cache and writes a `website_config_saved` audit log. If the audit log insert fails the change is undone and the response is `500`.

### Routes with no session/auth check — reviewed after this doc was generated

These were flagged by the doc-generation pass as having no `getSessionFromRequest`/`getSession` call despite living outside `app/api/public/**`. Each has since been individually reviewed and either fixed or confirmed intentional:

- **Fixed** — `GET /api/kitchen` and `PUT /api/kitchen` (`app/api/kitchen/route.ts`): now require a session (any authenticated staff role). Previously anyone could view live order/customer data on the kitchen display or change any order's status without logging in.
- **Fixed** — `GET /api/tables`, `POST /api/tables`, `PUT /api/tables` (`app/api/tables/route.ts`): now require a session (any authenticated staff role). Previously table layout/status was world-readable and world-writable.
- **Fixed** — `GET /api/orders/:id/items` (`app/api/orders/[id]/items/route.ts`): now requires a session, matching its `POST`/`PUT` siblings in the same file which already checked it. Previously any order's items/notes were readable by ID with no login.
- **Confirmed intentional, left as-is** — `GET /api/menu` (`app/api/menu/route.ts`): only returns `active=1` categories/items — the same data the public menu page already shows every customer. Not a data leak; no change needed.
- **Confirmed low-risk, left as-is** — `POST /api/seed`, `GET /api/seed`: both handlers are no-ops (see above), so being unauthenticated has no effect.
